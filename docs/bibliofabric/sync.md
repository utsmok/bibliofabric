# Sync usage

Every bibliofabric-based client ships two variants. The async code is the
single source of truth; the sync twins are generated from it with
[unasync](https://github.com/python-unasync/unasync) at dev time and committed.

| Async | Sync | What it is |
|---|---|---|
| `BaseApiClient` | `SyncBaseApiClient` | HTTP lifecycle: retries, pacing, auth, error mapping |
| `ResourceClient` | `SyncResourceClient` | typed per-endpoint operations (`get`, `search`, `iterate`, `batch_get`) |
| `FooClient` | `FooSyncClient` | a concrete client entry point |

Everything the package root exports is exported for both variants; import from
the package root, not from `bibliofabric._async` or `bibliofabric._sync`
directly.

## When to use which

Use the async variant inside `asyncio` applications (web servers, harvesters
with concurrent requests). Use the sync twin in scripts, notebooks, and code
that runs inside a running event loop: the sync path uses `httpx.Client`,
`time.sleep`, and threads, and never starts or touches an event loop.

## Example

```python
# async
async with StavrophoraClient(mailto="you@example.org") as client:
    work = await client.works.get("10.1038/nature12373")

# sync
with StavrophoraSyncClient(mailto="you@example.org") as client:
    work = client.works.get("10.1038/nature12373")
```

Both variants take the same parameters, raise the same errors, retry and page
the same way, and enforce the same rate limits.

## Guarantees

- Generated files carry the header `Generated by scripts/unasync.py; do not
  edit` and are committed. CI fails (`uv run python scripts/unasync.py
  --check`) when a generated file is stale; pre-commit runs the same check.
- Every behavior test in `tests/_async/` is generated into `tests/_sync/`, so
  each behavior is verified against both variants.
- Client authors keep their own packages' docs and quick starts showing both
  variants; see "Writing a client with sync support".
